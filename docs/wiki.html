IdemEngine — Stripe-style idempotency for Spring Boot 3

Last indexed: 2026-05-29 · Spring Boot 3.2.5 · PostgreSQL 15+

1. Overview

IdemEngine is a production-grade idempotency middleware for payment-class APIs. A merchant client sends POST /charges with an Idempotency-Key header, the network or server fails at any point, the client retries with the same key, and the customer is charged exactly once while receiving the byte-identical response. The implementation follows the design Stripe published in 2017 and Brandur Leach's companion post on the Postgres-backed implementation, with a four-phase recovery-point state machine.

Why this exists: a single boolean "seen this request" flag is nowhere near enough. The right primitive is a cursor through a state machine — a recovery point committed atomically with each phase's local mutations — so a crash between phases resumes correctly without re-executing foreign side effects.

2. State Machine

Four recovery points form a directed acyclic graph. Each transition is committed in its own @Transactional(REQUIRES_NEW) transaction alongside the local mutations of its phase, so the on-disk cursor exactly matches the on-disk work.

stateDiagram-v2 [*] --> started: tx1 INSERT key row
(locked, attempt 1) started --> customer_validated: tx2 INSERT ride(pending) + audit customer_validated --> external_api_called: PSP.charge(derivedKey="idem-${id}")
tx3 UPDATE ride.charge_id + audit external_api_called --> finished: tx4 stage receipt job
UPDATE response_body, unlock finished --> [*]: return cached response started --> started: retry resumes here customer_validated --> customer_validated: retry resumes here
(PSP dedup via derived key) external_api_called --> external_api_called: retry resumes here

States are an append-only enum in RecoveryPoint.java. Code that encounters an unknown recovery_point hard-fails — silently skipping a phase is a correctness bug.

4. Database Schema

Five tables, defined in V1__schema.sql:

TablePurposeKey invariants
idempotency_keys The cursor row. One per logical request. UNIQUE (user_id, key) — per-tenant scope. recovery_point is the state-machine cursor.
rides The business record being charged for. UNIQUE (user_id, idempotency_key_id) — no duplicate ride per request.
audit_logs One row per state transition. UNIQUE (idempotency_key_id, attempt_no, action, to_state) — phase retries write the same row at most once.
staged_jobs Transactionally-staged work (e.g. receipt email). UNIQUE (idempotency_key_id, job_name) — phase 4 retry doesn't enqueue twice.
users Auth principal. Owns the FK target for idempotency_keys.user_id.

5. Orchestrator no @Transactional

The IdempotencyService.execute() method drives the state machine. It has no @Transactional annotation on purpose: every phase commits in its own REQUIRES_NEW transaction inside PhaseTransactions, and the PSP call happens between phases, outside any DB transaction.

public IdempotencyOutcome execute(long userId, String key, String method, String path,
                                  String canonicalBody, String bodyHash) {

    AcquireResult ar = acquireWithConcurrentInsertRetry(...);    // tx1

    return switch (ar) {
        case AcquireResult.Cached c     -> IdempotencyOutcome.ok(c.statusCode(), c.body());
        case AcquireResult.Conflict c   -> IdempotencyOutcome.conflict(c.retryAfterMs());
        case AcquireResult.BodyMismatch -> IdempotencyOutcome.bodyMismatch();
        case AcquireResult.Fresh f      -> runStateMachine(f.keyId(), RecoveryPoint.STARTED, ...);
        case AcquireResult.Resumed r    -> runStateMachine(r.keyId(), r.recoveryPoint(), ...);
    };
}

6. Phase Transactions REQUIRES_NEW

Every method on PhaseTransactions is annotated @Transactional(propagation = REQUIRES_NEW). This is the single most important detail in the codebase: recovery-point commits must NOT roll back with any downstream failure.

MethodTxRecovery transition
acquireOrServetx1(none) → row INSERT or lock acquire
runStartedPhasetx2started → customer_validated
persistExternalCallResulttx3customer_validated → external_api_called (or → finished on decline)
runFinalizePhasetx4external_api_called → finished

The PSP call sits between tx2 and tx3, in the orchestrator. If the JVM dies after the PSP returns 200 but before tx3 commits, the next attempt resumes at customer_validated and reissues the PSP call with the same derived key — the PSP returns the cached charge id; tx3 commits with the correct value; no double charge.

7. Nested Idempotency load-bearing

Every external/payment call must carry a derived idempotency key. Skipping this defeats the entire system: the outer key prevents a second ride row in our DB, but a second PSP call would create a second charge at the PSP.

// In IdempotencyService.runExternalCallPhase:
String derivedKey = "idem-" + keyId;        // BIGINT row id, deterministic across retries
PspChargeResult result = psp.charge(req.amount(), req.currency(),
                                    req.customerId(), derivedKey);

The derived key has three properties:

  1. Deterministic across retries — row id assigned once at INSERT; every retry references the same row.
  2. Globally unique within the system — BIGINT primary key, so two tenants using the same inbound key string produce different downstream keys.
  3. Opaque to client — clients cannot influence it, so a malicious client cannot cause downstream collisions.

The ExternalPaymentClient.charge interface takes derivedIdempotencyKey as a required parameter — accidental omission is a compile error, not a runtime bug.

8. Concurrency Model

Two layers of mutual exclusion:

  1. Postgres row lock via SELECT … FOR UPDATE — held only within a single transaction. Guards the current TX's view from concurrent writers.
  2. locked_at timestamp — held across transactions. A row is considered "in progress" if locked_at > now() - 90s. Older than that, the previous holder is presumed dead and the next entrant reclaims by stamping a fresh locked_at.

The 90-second staleness threshold is calibrated to exceed the PSP timeout (80s) by 10 seconds, absorbing JVM stop-the-world pauses and similar.

Deadlock-impossible: every transaction locks exactly one idempotency_keys row, identified uniquely by (user_id, key). No two transactions can ever hold locks on the same pair of rows in opposite order.
